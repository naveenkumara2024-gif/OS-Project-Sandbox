# Stage 5: Integration

## 1. Goal

At the end of this stage an AI harness can use AegisEngine without a human typing commands, and the human still decides what reaches the real project. A long-running local gateway (`aegis serve`, HTTP over a mode-0600 Unix socket) and an MCP server over stdio (`aegis mcp`) expose the same engine: start a run, stream its output as NDJSON events, cancel it, keep a **session** whose overlay accumulates changes across several runs, fetch the diff, and `commit` only the paths the human approved, bound to the exact diff that was shown. An optional **egress broker** gives a cell one narrow, audited, hostname-allowlisted path to the internet without giving it a network interface. A `PreToolUse` hook and example `.mcp.json` and settings make the safe path the easy one. The gate is an end-to-end session in which a harness runs code, repairs it, reads the diff, and a commit lands only after approval. Escape probes 5 and 20 are re-run with the broker on, and three new probes (21 to 23) attack the broker, the gateway and the session model.

## 3. In scope / out of scope

In scope:

- **Engine core** (`src/engine/`): one in-process service with run, cancel, status, diff, commit, discard, sessions and admission control. Both front ends are thin adapters over it.
- **Sessions**: a session owns one workspace (lower, overlay upper) and survives across runs until `commit`, `discard`, idle expiry or engine shutdown policy. Server-assigned unguessable ids. One run at a time per session.
- **Streaming**: the supervisor emits bounded stdout and stderr chunks, limit warnings and the final receipt as events; `cancel` uses the same kill procedure as a timeout.
- **Gateway** (`aegis serve`): HTTP/1.1 over a Unix socket in `$XDG_RUNTIME_DIR/aegis/`, mode `0600`, no TCP listener, strict limits and timeouts.
- **MCP server** (`aegis mcp`): dual-era stdio, tools `run`, `status`, `diff`, `commit`, `discard`.
- **Commit approval**: `commit` takes an explicit path list and the SHA-256 of the change list the approver saw; a mismatch refuses and returns the new diff.
- **Egress broker**: `network.mode: "brokered"`, a host-side HTTP `CONNECT` allowlist proxy per cell over a Unix socket, an in-cell forwarder, DNS resolved on the host with private, loopback, link-local, CGNAT and WSL-gateway results refused, an audit log returned in the receipt and appended to a host file.
- **Policy additions** (ceiling): `network_ports`, `max_cells`, `memory_budget_mb`, `max_sessions`, `session_idle_s`.
- **A `PreToolUse` hook**, example `.mcp.json` and example Claude Code settings, docs.
- **Escape probes 21 to 23**, probes 5 and 20 re-run with the broker, fast-check properties for every new parser, an end-to-end MCP session test.

Out of scope (and the stage that owns it):

- The ablation matrix, benchmarks and fuzz campaigns: **Stage 6**. Jazzer.js is proposed for Stage 6 (section 11 item 7).
- A TCP listener, TLS interception, authentication beyond filesystem permissions, multi-user operation, UDP or DNS inside the cell, non-HTTPS egress, plain-HTTP proxying.
- A `loopback`-only network mode (section 11 item 8).
- Applying deletions on `commit` (section 11 item 5). The Stage 3 leftovers (`fsop` fuzz target, positional differ, `RLIMIT_FSIZE`) stay with Stage 3, except that the `changes.json` shape check disappears naturally when session metadata moves to a strict schema (section 4.2).
- Anything about Windows-native or WSL1.

## 4. Design

### 4.1 Process model

```
harness ──stdio JSON-RPC──▶ aegis mcp ─┐
SDK agent ──HTTP/Unix socket──▶ aegis serve ─┤──▶ Engine ──▶ runCell (Stage 4) ──▶ aegis-cell boot/init
                                              │             └─▶ Broker (per brokered cell) ──▶ internet
human ──CLI──▶ aegis run | commit | discard ──┘
```

`aegis mcp` and `aegis serve` each embed one `Engine` in the same process (one event loop, no threads, CLAUDE.md 5.2). They do not talk to each other: two front ends running at once have separate in-memory session tables, and each session's directory carries a strict-schema `session.json` naming its owner pid so the CLI and the startup sweep can tell live from dead.

Both must run inside a delegated cgroup subtree (ADR 0003). The documented way is the harness launching `systemd-run --user --scope --quiet --collect --same-dir -- node /abs/dist/main.js mcp` (section 11 item 6). Outside a delegated subtree every run is refused with the existing hint; nothing is weakened.

### 4.2 Sessions

- A request that carries `files` or `workspace` and no `session` creates a session; the response returns its `session` id. A request with `session` reuses it. A request with neither is a stateless run (today's behaviour without a workspace).
- Ids from the gateway and MCP are server-generated, 128 bits from `crypto.randomBytes`, hex, prefixed `s-`. The one-shot CLI keeps using the request `id` as the session id (existing behaviour, same regex), so `aegis commit <id>` and `discard <id>` keep working. A caller-supplied id is never used as a path component without the existing `^[A-Za-z0-9_.-]{1,64}$` check and a `lstat` that the directory is a real directory owned by this user (Stage 3 report item 10 is closed by never accepting a client id on the gateway).
- A session runs one cell at a time. A second `run` while one is running is refused with `busy`, not queued.
- Later runs may carry more `files`; they are written into the **upper** layer by the control plane (same relative-path validation as inline files today), so they show up in the diff as changes, which is what they are. Step 1 verifies that a host write into an unmounted overlay upper layer is read back correctly by the next mount (including over an existing lower file and over a whiteout). If it is not, later runs may only run commands (section 11 item 3 is not needed for this; it is an implementation fallback recorded in the report).
- The upper-layer disk cap (`disk_mb`) is already cumulative over the session (the poll measures the whole upper tree), so repeated runs cannot grow past it.
- `session.json` (strict zod schema, written by the control plane, read back through the schema): id, owner pid, created and last-used times, source path or null, lower and upper paths, state. This replaces the shape-checked `changes.json` read in `main.ts` (CLAUDE.md 6.4).
- Lifetime: ends on `commit` (when every approved path was applied or refused and the owner asks to close; default keeps it for follow-up), `discard`, idle timeout `session_idle_s` (ceiling, default 1800), or `max_sessions` exceeded (the oldest idle session is expired first; if none is idle, the new one is refused). A sweep timer runs every 60 s; a startup sweep removes session directories whose owner pid is dead and whose last use is older than the idle timeout. Discard uses the existing `discardWorkspace`.

### 4.3 Run lifecycle, events, cancellation

- `Engine.startRun(request, session?)` validates, resolves the manifest, waits for admission, and returns a run handle: `{ runId, events: AsyncIterable<RunEvent>, result: Promise<CellResult>, cancel(): void }`.
- Event types (all carry `seq`, monotonically increasing per run, and `t_ms` since start): `queued`, `started`, `stdout` and `stderr` (`data` as UTF-8 text with invalid bytes replaced, at most 8 KiB per event, coalesced for 50 ms), `limit_warning` (`limit` in `wall | cpu | memory | output | disk | pids`, `used`, `max`, once per limit at 80 %), `receipt` (the `CellResult`), then the stream ends. The supervisor gains an `onOutput` callback; the final receipt still holds the full bounded stdout and stderr, so events are a convenience and never the only copy.
- Each subscriber has a bounded queue (256 KiB). A slow subscriber loses chunk events (a `dropped` counter on the next delivered event says how many bytes), never the `receipt`. The engine never blocks the cell on a subscriber.
- Event history for a finished run is kept for 5 minutes and at most 64 runs (oldest dropped), each capped at 1 MiB, so a late `GET .../events` replays then ends.
- **Cancellation** calls the same kill procedure as the wall-clock timeout (`cgroup.kill`, helper `K`, then the existing backstops). The termination cause is a new `cancelled` (section 11 item 3), with `limits_hit` empty. A run cancelled while still queued never starts.
- **Admission control**: at most `max_cells` cells run at once (ceiling, default 4) and the sum of their `memory_mb` may not exceed `memory_budget_mb` (ceiling, default 4096). A run that does not fit waits in a FIFO queue of at most 16 for at most 30 s, then is refused with `busy` and a `retry_after_ms` hint. Queue position is reported by `queued` events.

### 4.4 Gateway (HTTP over a Unix socket)

- Socket path `$XDG_RUNTIME_DIR/aegis/gateway.sock`. The directory is created `0700` and must be owned by the user, not a symlink, and mode `0700`, or the server refuses to start. The socket is made `0600` with a `umask(0o177)` window around `listen` (umask is process-wide, so this is done before the server accepts anything). A stale socket is removed only after a connect attempt shows nobody is listening. No TCP listener exists in the code.
- Built on `node:http` (no framework). Hard limits: request line and headers 16 KiB, at most 32 headers, `headersTimeout` 5 s, `requestTimeout` 30 s for bodies, `keepAliveTimeout` 5 s, body at most `MAX_REQUEST_BYTES` (256 KiB), counted while reading and enforced before parsing (`Content-Length` over the cap is refused at once; chunked bodies are counted). At most 32 concurrent connections. `Content-Type: application/json` is required on POST. Anything not in the table is `404`; a known path with another method is `405`.

| Method and path | Purpose | Success |
| --- | --- | --- |
| `GET /v1/status` | engine facts: version, delegated cgroup yes/no, helper present, layers last seen, active cells, sessions | `200` JSON |
| `POST /v1/runs` | body is the run request (section 4.5 schema) | `202` `{ run, session }` |
| `GET /v1/runs/{run}` | state and, when finished, the receipt | `200` JSON |
| `GET /v1/runs/{run}/events` | NDJSON event stream (`application/x-ndjson`) | `200` chunked |
| `POST /v1/runs/{run}/cancel` | cancel | `202` |
| `GET /v1/sessions/{s}/diff` | change list, hashes and text patches (bounded), `changes_sha256` | `200` JSON |
| `POST /v1/sessions/{s}/commit` | `{ paths, expected_changes_sha256, dest? }` | `200` per-path outcomes |
| `DELETE /v1/sessions/{s}` | discard | `200` |

- Errors are `{ "error": { "code", "detail" } }` with codes from a closed set (`invalid_request`, `too_large`, `not_found`, `busy`, `stale_diff`, `policy`, `isolation_unavailable`, `internal`); `detail` never contains request content. Path parameters are validated against `^(s-[0-9a-f]{32}|r-[0-9a-f]{32})$` before any lookup.
- Peer identity: Node cannot read `SO_PEERCRED`. Access control is the `0700` directory and `0600` socket, which is sufficient on a single-user machine and is stated as the limit in the docs.

### 4.5 Request, MCP tools, and the commit approval gate

The run request is today's schema plus `session` (optional, validated id). `manifest.workspace.mode` stays `overlay`. The MCP tool input schemas are generated from the same zod schemas where possible (hypothesis: zod 4's JSON Schema export is usable; step 1 checks, with a hand-written schema as the fallback, kept in a test that fails if the two disagree).

| MCP tool | Does | Notes |
| --- | --- | --- |
| `run` | start a run and wait for the receipt | creates or continues a session; returns the full receipt as `structuredContent` and a JSON text block; stdout and stderr capped at 64 KiB each in the MCP result with a `truncated` flag |
| `status` | engine facts, active cells, sessions, the last isolation level | read-only |
| `diff` | change list and patch for a session, with `changes_sha256` | read-only |
| `commit` | apply approved paths | `paths` (required, non-empty) and `expected_changes_sha256` (required) |
| `discard` | delete a session | |

- Tool-level problems (unknown session, busy, stale diff, invalid arguments, policy refusal) are results with `isError: true`. A run that ends in a non-zero exit, a timeout, an OOM or an isolation refusal is **not** an error: the receipt is the data. Unknown tools and malformed JSON-RPC are JSON-RPC errors.
- **Commit approval.** `commit` recomputes the change list from the session's upper layer and compares its canonical SHA-256 with `expected_changes_sha256`. A mismatch refuses with `stale_diff` and returns the current diff, so the approver always approves exactly what is applied. Matching paths go through the existing `commitChanges` (`aegis-cell fsop`, `openat2` confinement, symlink, device, FIFO, set-uid, size, git-hook refusals). The destination is the session's own `workspace.source`, which must be inside a `commit_roots` entry; a session created from inline files only has no destination and must pass `dest`, which `resolveCommitRoot` checks against `commit_roots`. The model never chooses a destination outside the policy.
- **What the human gate is, honestly.** The approval is the harness's permission prompt on `mcp__aegis__commit` (the example settings put it under `ask` and everything else under `allow`), plus the diff binding above. An agent that also holds an unrestricted shell as the same user can already edit the project directly, so AegisEngine protects against *generated code*, not against a compromised harness; the hook is a guide rail, not a boundary. An engine-side out-of-band approval was considered and rejected because the agent's shell shares the user's identity and could run the approver itself. Both statements go in the docs and the report.

### 4.6 MCP server (`aegis mcp`)

- Hand-written JSON-RPC 2.0 over stdio, no SDK (CLAUDE.md 2 forbids undeclared dependencies; the protocol surface used is small). One message per line; a line over 1 MiB or invalid UTF-8 or JSON is a `-32700` parse error with `id: null`; nothing but valid messages is ever written to stdout; diagnostics go to stderr as typed log events. Prototype-pollution keys are rejected as elsewhere.
- Dual-era: `server/discover` (modern) and `initialize` plus `notifications/initialized` (legacy) are both answered; `tools/list`, `tools/call` and `ping` work in both; the list of protocol versions it speaks is fixed in step 1 from the specification pages and is returned in `UnsupportedProtocolVersionError` `data.supported`. For `initialize`, the requested version is echoed if supported, otherwise the latest supported is returned. Capabilities: `tools` only (`listChanged: false`).
- `notifications/cancelled` for an in-flight `tools/call` cancels its run (section 4.3) and sends no further message for that id. Closing stdin ends the process after cancelling and discarding nothing (sessions persist for the CLI and the sweep).
- Request concurrency: at most 8 in-flight `tools/call`s; more are answered with a JSON-RPC error. Each call has the run's own wall limit plus a 5 s margin as its overall timeout.

### 4.7 Egress broker

Preserves contribution 2 (the cell has no interface to the world; the receipt says exactly what path it has) and contribution 4 (the allowlist is in the manifest, clamped by the ceiling, hashed).

- **Manifest**: `network.mode` becomes `"none" | "brokered"` (default `none`). `network.allow` is clamped against the ceiling's `network_allow` exactly as in Stage 4. If the mode is `brokered` and nothing survives the clamp, the resolved mode is `none` and the clamp list says so (`network.mode` requested `brokered`, granted `none`). The ceiling gains `network_ports` (default `[443]`); a CONNECT to any other port is refused.
- **Host side** (`src/broker/`): one listening Unix socket per brokered cell inside the per-cell directory, mode `0600`, bind-mounted into the cell as `/.aegis-broker.sock`. It speaks one thing: HTTP `CONNECT host:port HTTP/1.1`. The parser is strict and bounded: request line at most 512 bytes, headers at most 8 KiB, 5 s to complete, any other method is `405`. The host must be an ASCII hostname that is in the resolved allowlist after lower-casing and removing one trailing dot; IP literals, brackets, userinfo (`a@b`), embedded NUL, percent-escapes and spaces are refused before any lookup.
- **DNS and address policy**: the broker resolves with `dns.promises.lookup(host, { all: true })` on the host. **Every** address returned must be public, otherwise the name is refused (a name that maps both to a public and a private address is a rebinding attempt). Refused: `0.0.0.0/8`, `10/8`, `100.64/10`, `127/8`, `169.254/16`, `172.16/12`, `192.0.0/24`, `192.0.2/24`, `192.168/16`, `198.18/15`, `198.51.100/24`, `203.0.113/24`, `224/4`, `240/4`, IPv6 `::`, `::1`, `fc00::/7`, `fe80::/10`, `ff00::/8`, `2001:db8::/32`, any IPv4-mapped or NAT64-embedded address whose IPv4 part is refused, and the **host's own default gateway and its subnet** read from `/proc/net/route` when the broker starts (the WSL gateway range). The connection is then made to the validated address literal, never to the name again, so the check and the use cannot differ.
- **Tunnel**: after `200 Connection Established`, bytes are relayed with bounded buffers and backpressure. Per cell: at most 16 concurrent tunnels, 60 s idle timeout, 10 min lifetime, 64 MiB in each direction in total, then the tunnel is closed and the audit says why. These are constants in this stage (section 11 item 9).
- **Audit**: one entry per attempt, allowed or denied: `ts`, `host`, `port`, `decision` (`allow | deny`), `reason` (closed set: `not_allowlisted`, `port_not_allowed`, `bad_request`, `bad_method`, `private_address`, `resolve_failed`, `connect_failed`, `limit`, `ok`), `resolved` (the single address used, for allowed entries), `bytes_up`, `bytes_down`, `duration_ms`. The receipt carries up to 256 entries and `audit_dropped`. The same entries are appended as JSON lines to `$XDG_STATE_HOME/aegis/audit.jsonl` (default `~/.local/state/aegis`, directory `0700`, file `0600`, rotated once at 10 MiB) with the run id and `manifest_sha256`. Payload bytes are never logged.
- **In-cell forwarder** (new native code, justified: Node never runs in a cell and `socat` is absent): `aegis-cell fwd`, a mode of the static helper, about 150 lines. It listens on `127.0.0.1:3128`, and for each accepted connection (at most 16) connects an `AF_UNIX` stream socket to `/.aegis-broker.sock` and relays with `poll(2)` and fixed buffers. It parses nothing, so it has no input parser to fuzz; the bytes are the broker's to validate. `init` starts it before the payload; the payload's environment gains `HTTP_PROXY`, `HTTPS_PROXY`, `http_proxy`, `https_proxy` set to `http://127.0.0.1:3128` (fixed names and value, CLAUDE.md 6.1 item 5). The forwarder runs with the same capability drop, `no_new_privs` and seccomp filter as the payload, and its own Landlock domain that allows only TCP bind of port 3128.
- **Loopback and Landlock**: `boot` brings `lo` up inside the new network namespace (it owns that namespace and still has its capability at that point; a socket `ioctl(SIOCSIFFLAGS)` read back with `SIOCGIFFLAGS`) only when the spec says brokered. The payload's Landlock ruleset (Stage 4) gets one added rule in that case: TCP connect to port 3128 only. Every other connect and every bind stays denied, so a program that ignores the proxy variables fails closed. New receipt layers `loopback` and `broker` are reported only after being observed (`lo` flags read back; the forwarder reports `listening` through a pipe after `listen` succeeds); a manifest may `require` them.
- **What the payload can do through it**: reach any allowlisted `host:443` the broker accepts. It can still exfiltrate data to an allowlisted host (the broker sees hostnames, not encrypted contents). The blueprint says the same; the docs and the report repeat it and recommend narrow allowlists.
- A payload can also connect straight to the bind-mounted broker socket path without the forwarder; that gives it nothing the proxy variable does not, because the broker enforces the same rules on every connection.

### 4.8 Logging, state directories, engine launch

- New `src/util/logger.ts`: typed event objects with allow-listed fields, JSON lines to stderr (for `mcp`, as the spec permits) or the log file `$XDG_STATE_HOME/aegis/engine.log` (for `serve`), always with run id and `manifest_sha256` where known. It cannot be handed arbitrary values (CLAUDE.md 5.3). Events: run queued, started, finished (cause, level), cancelled, refused, session created, expired, committed, discarded, broker allow or deny (host and reason only), gateway request rejected (reason code only).
- Policy lookup (section 11 item 2): `AEGIS_POLICY_FILE`, then `$XDG_CONFIG_HOME/aegis/policy.json` (default `~/.config/aegis/policy.json`). If neither exists the engine refuses with layer `policy`; it no longer falls back to the repository's `policy.default.json`, which is a template to copy, because in an MCP setup the repository is usually the very workspace the agent can write to (CLAUDE.md 6.4).

### 4.9 The five contributions

1. **Diff-then-commit**: strengthened. Sessions accumulate in the overlay; nothing reaches the project without `commit`, which is bound to the exact diff hash and refused for hooks, symlinks and the rest as in Stage 3.
2. **Fail-closed receipts**: a brokered cell only reports `broker` and `loopback` after observing them; a manifest that requires them is refused otherwise; the receipt states the network path (`mode`, `egress`, and the audit).
3. **Termination causes**: adds `cancelled`; the classifier and hints are extended, nothing is renumbered.
4. **Manifests as policy-as-data**: `brokered` and the allowlist are in the manifest, clamped, hashed; five new ceiling keys.
5. **Escape corpus**: probes 21 to 23 and the broker variants of 5 and 20.

## 9. Risks and mitigations

- **MCP specification drift.** The protocol has changed eras recently. Mitigation: dual-era server, version list fixed from the spec in step 1, tests for both handshakes, and a documented fallback to the legacy era if a harness fails the modern probe.
- **Host writes into an overlay upper layer** might not be read back correctly by the next mount. Mitigation: step 1 tests it; fallback is that later runs only run commands, recorded as a deviation.
- **Landlock network rules or loopback bring-up not behaving as hypothesised.** Step 1 tests both before any code depends on them. If the port rule cannot be expressed, the brokered mode is cut from this stage (section 11 item 2) and everything else ships.
- **Broker bypass or SSRF.** Address checks happen on the resolved literal that is then used; rebinding is closed by refusing mixed answers; the gateway range is read at start. Residual: an allowlisted host can still be an exfiltration channel, and a hostname allowlist cannot see inside TLS.
- **Resource exhaustion by a client.** Every parser is bounded; connection, queue, session and tunnel counts have hard caps; slow clients time out; subscribers cannot slow a cell.
- **Slow subscriber or runaway output** filling memory: bounded queues, chunk drops with a counter, the receipt is never dropped.
- **Orphaned cells or session directories after a crash.** The Stage 2 reaper and a new startup sweep for sessions; tests assert nothing is left after cancel, expiry and a killed engine.
- **The permission prompt is the human gate and a harness can be misconfigured to allow `commit`.** The diff-hash binding limits the damage to approved-looking diffs, but the prompt is the real control and the docs say so (section 4.5).
- **Scope.** This is the largest stage. The steps are ordered so the broker is last (steps 6 to 8) and can be split into its own stage without losing the rest (section 11 item 2).

## 10. Rollback

All work goes on `stage/5-integration`. Back out with `git revert` or by deleting the branch. No cgroup configuration, system file or package is touched. Session directories and the gateway socket live under `$TMPDIR` and `$XDG_RUNTIME_DIR/aegis` and are removed by `discard`, expiry or the startup sweep; the state directory `~/.local/state/aegis` (audit and engine logs) is safe to delete.
